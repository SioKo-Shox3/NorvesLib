> 本体（`CLAUDE.md` / `AGENTS.md`）には「適用範囲」「開発段階ダイヤル」「規模トリアージ」「運転規律」が常駐しており、本書はそれらの前提の上に載る。モデル選定は `model-playbook.md`。

## 役割分担の原則

- **オーケストレーター**が担うもの: 工程分割、設計判断、順序付け、スコープ割り当て、サブエージェント結果の統合、検証実行、コミット境界管理、最終受け入れ。
- オーケストレーター自身は **具体的なフェーズ計画の作成・ファイル編集・自分が監督した実装のレビューを行わない**。これらはサブエージェントに割り当てる。
- **実装担当とレビュー担当は必ず別エージェント**にする。
- **実装はメイン側 `implementer` サブエージェントへ委譲する**（メインエージェント自身は書かない。難所は上位モデルで起動）。**実装をパートナーAIへ移譲しない**（クロスCLI実装移譲は廃止 2026-07-12 — パートナーAIの役割はレビュー二次と相談のみ）。プラグイン経由の委譲は使わない（2026-07-05）。
- **レビューは Claude＋Codex のダブルチェック（必須ゲート）**にする。計画レビュー・実装レビューとも一次を最上位 Claude（実装者と別エージェント）、二次を独立した Codex が行う。二次は**直接 CLI（`codex exec --sandbox read-only`、同期）で呼び、プラグインを経由しない**。詳細は「Codex への委譲とレビューのダブルチェック」を参照。
- 各工程は独立してレビュー・検証・コミットできる最小単位にする。クリーンに分割できない場合は理由を述べ、最小の実用的チェックポイントを定義する。先行する依存フェーズが実装レビューと検証ゲートを通過するまで、後続フェーズの実装を始めない。

## 実装委譲とレビューのダブルチェック

実装はメイン側 `implementer` サブエージェントへ委譲し、レビューは Claude と Codex の二重化で品質を担保する（2026-07-05 改定でプラグイン経由の委譲を廃止、2026-07-12 にクロスCLI実装移譲も廃止 — Codex の実装力は Codex をメインとして使うことで活かす。Codex 二次レビューは直接 CLI で必須のまま）。これは本書の「工程（フェーズ）の流れ」および `Docs/agent-guide/model-playbook.md`「モデル選定」に優先して適用する既定方針。

- **実装は `implementer` サブエージェントが担当**（承認済み計画と許可パスを渡す。委譲文に「同一アプローチ2回失敗で停止して報告（ループ禁止）」条項を必ず含める。難所は上位モデルで起動）。パートナーAIの CLI へ実装を渡さない。プラグイン（`codex:rescue`）も経由しない。
- **委譲時に必ず渡す情報**: 対象フェーズと目的、許可/禁止の書き込みパス、`Docs/agent-guide/coding-style.md`「コーディング規約」の独自型ルール（コンテナ/スマポ/ログ/計測）、行末・BOM ルール（既存は CRLF 維持、新規ソースは UTF-8+BOM+CRLF）、期待する出力形式（変更ファイル・実行した検証・未解決リスク・前提）。出力は「提案物」として扱い、オーケストレーターが diff を統合観点で検査してから受け入れる。
- **レビューはダブルチェック（必須ゲート）**: 計画レビュー・実装レビューとも、一次レビューを最上位 Claude（実装者とは別エージェント）が行い、加えて二次レビューを独立した Codex が行う。二次は**直接 CLI（`codex exec --sandbox read-only`、同期実行・ポーリング不要）**で呼ぶ。呼び出しが失敗した場合のみ verifier の反証で代替し、Codex ゲートを省略した旨を必ず報告する。
- **収束規則 — レビューは最大2周（2026-07-13 新設）**: 依頼文で指摘を **blocking**（正しさ・安全・データ損失・エンジンクリティカル規約違反）/ **non-blocking**（改善提案）に分類させ、修正必須は blocking のみ。2周目は**前回指摘への対応 diff だけ**を確認し、新規指摘は blocking のみ受理。**3周目は無い** — 残った non-blocking は「残課題」として完了報告に記録し、返済サイクル（code-gardening）へ送る。修正→再レビューの無限往復は実測済みの停止不能パターン。
- **自己レビュー禁止（独立性の担保）**: 実装した本人（同一エージェント・同一セッション）に自分の変更をレビューさせない。一次レビューは実装者と別の最上位 Claude、二次はクリーンな文脈の Codex（非メイン側 AI）で二重化する。
- **エンジンクリティカルな変更**（Public API・RHI/Vulkan・RenderThread・メモリ・ジョブ・アセットロード・Object/Resource 寿命）は、レビューのダブルチェック（Claude 一次＋Codex 二次）を省略しない。

## デュアルメイン運用（2026-07-04 設定）

- **オーケストレーター = ユーザーが起動した側。** Claude Code は `CLAUDE.md`、Codex は `AGENTS.md`（完全同一ミラー）を読むため、切り替え操作は存在しない — Codex に指示を出せば Codex がメインとして本書どおりに振る舞う。
- **二次レビューは常に非メイン側の AI**（Claude メイン → Codex 二次、Codex メイン → Claude 二次）。ベンダーの異なるモデルは失敗モードも異なるため、クロスチェックが構造的に保証される。呼び出しは**直接 CLI**（`codex exec` / `claude -p`）で行い、プラグインを経由しない。
- **Codex がメインのとき:** `.codex/agents/` のサブエージェント群（researcher / planner / plan_reviewer / test_designer / implementer / impl_reviewer / verifier）で工程を回し、相談・二次レビューは Claude ヘッドレスで行う。例: `claude -p "<相談ブリーフ>" --model opus --permission-mode plan`（読み取り専用の相談）、レビューは `.claude/agents/impl-reviewer.md` を読ませて役割を継承させる。**実測(2026-07-06): Codex のサンドボックス内からはネットワーク遮断で失敗する — 対話セッションで「サンドボックス外実行」を承認する形で呼ぶこと（非対話 `codex exec` 内からは不可）。**
- **相互ヘルプ:** どちらがメインでも、同一フェーズで反証・手戻りが2回続いたら、回数を重ねる前にパートナーAIへ構造化ブリーフ（問題/証拠/試したこと/具体的な質問）で相談する。回答は助言 — 採否はメインが判断する。
- 下記の PreToolUse ガードは Claude がメインのときのみ作動する。

## ハーネスによる強制（2026-07-03 展開）

この方針は文書だけでなくフックで強制される（Sembazuru で実証済みの方式。原型はリポジトリ外の `../claude-workflow-template`）。

- `.claude/hooks/enforce-codex-impl.mjs`（PreToolUse）が、メインスレッドによる C++/シェーダーソース（`.cpp/.h/.hpp/.inl/.glsl/.hlsl/.slang` 等）の `Edit`/`Write` を物理的にブロックする。実装は `implementer` サブエージェントへ委譲する。CMakeLists・`.md`・`.json` 等の設定/文書はブロックされない。
- `.claude/hooks/session-start-reminder.mjs`（SessionStart）が毎セッション冒頭にこの方針を注入する。
- 意図的な一時解除（ユーザー承認必須・1 セッション限り）: 環境変数 `NORVESLIB_ALLOW_DIRECT_EDIT=1` を設定して再起動。共有ファイル（公開ヘッダ等）の順次編集もまず Codex への順次委譲で行い、解除は最終手段にする。
- **新しい作業ツリーを勝手に作らない**（Codex メイン時は `.codex/hooks/workspace-guard.mjs` が
  `git worktree add` をブロック — 2026-07-12 新設）: 新ツリーは AGENTS.md が分岐時点の旧版・
  フックはパス単位 trust 未登録で無言全滅する（実測）。隔離が必要ならユーザー承認+
  ミラー最新化+trust 登録（trust-hooks.mjs）+session_start 発火実証までを同一タスクで。
  承認済みの一時解除: `NORVESLIB_ALLOW_WORKSPACE=1`。
- `.claude/settings.local.json` はマシンローカル（フック配線を含む）。別マシンでは `claude-workflow-template/deploy.ps1` で再展開する。

## 工程（フェーズ）の流れ

1. **調査 (Investigation)** — 既存コード・依存・命名規約の把握。読み取り専用。
2. **計画 (Planning)** — フェーズごとに具体的な実装計画を書く。計画には次を含める:
   - フェーズの目的と期待される挙動変化。
   - 影響するモジュール・公開 API・具体的なファイル/ディレクトリ。
   - 実装方針（所有権/寿命ルール、依存方向、データ構造、スレッド前提、移行/互換戦略）。
   - そのフェーズで走らせるテスト/検証コマンド（focused ターゲット + CTest）。
   - リスクレベルと、エンジンクリティカルな変更のロールバック/封じ込め方針。
   - コミット境界（コミット可能になる条件）。
3. **計画レビュー (Plan Review)** — API 境界、所有権モデル、依存方向、リソース寿命、スレッド安全性、CMake/テスト登録、後方互換、コミット単位の妥当性を確認。エンジンクリティカルな変更（Public API・RHI/Vulkan・RenderThread 挙動・メモリ管理・ジョブスケジューリング・アセットロード・シェーダーパイプライン・Object/Resource 寿命）は、変更が小さく見えても必須。一次レビュー（最上位 Claude）の後、Codex による独立した二次レビュー（直接 CLI で実行するダブルチェック）も通す。
4. **実装 (Implementation)** — 承認された計画に沿って編集。**`implementer` サブエージェントへ委譲する**（メイン自身は編集しない。難所は上位モデルで起動。クロスCLI実装移譲は廃止 2026-07-12）。渡すタスクには対象フェーズ・目的・許可/禁止の書き込みパス・独自型ルール・行末/BOM ルール・期待する出力を明示し、出力は提案物として統合前に diff を検査する。サブエージェントには支援するフェーズと目的、許可/禁止の書き込みパス、期待する出力形式（変更ファイル・実行した検証・未解決リスク・前提）、タスク種別（read-only/実装/テスト作成/レビュー）を明示する。書き込みスコープはサブエージェント間で重複させない。公開ヘッダ・中央 CMake・ビルド設定・シリアライズスキーマ・コア寿命管理など共有ファイルは単一オーナーかオーケストレーターが順次編集する。
5. **実装レビュー (Implementation Review)** — 実 diff を承認済み計画と突き合わせ、公開 API 形状、所有権/破棄経路、依存方向、共有ヘッダ影響、生成/ビルドファイルの除外、CMake 登録、テストカバレッジ、サブエージェント出力を確認。**blocking 指摘のみ次に進む前に修正する**（non-blocking は残課題へ — 上の収束規則参照、レビューは最大2周）。計画した検証コマンドを実行できなかった場合は理由と残存リスクを記録する。この一次レビュー（最上位 Claude）に加え、Codex による独立した二次レビュー（直接 CLI で実行するダブルチェック）を通す。実装者と同一エージェントに自己レビューさせない（Codex 実装分は Claude 一次＋クリーン文脈の別 Codex で二重化する）。
6. **統合・検証・コミット** — サブエージェント出力は提案物として扱い、オーケストレーターが diff を統合観点で検査し、計画との一致・API 境界・所有権を確認し、関連検証を再実行してから受け入れる。フェーズ完了ゲート: 実装統合済み・実装レビュー完了・関連ターゲットがビルド・CTest/focused テストが通過・レンダリング/ゲーム可視の変更にはログ/スクショ（実用的なら）。タスク完了時は全フェーズをコミットするか、理由を述べて意図的に未コミットとし、作業ツリーの残状態を報告する。
