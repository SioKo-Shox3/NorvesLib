# モデル選定

> `CLAUDE.md` / `AGENTS.md`（working agreement）から移設した詳細規約。本体には索引だけを残し、全文はここが正本。
> モデルの実測（eval fixture の回し方）は `model-evals.md`、工程・レビュー体制は `orchestration.md`。

---

**判断の質が後工程全体を左右する役割（計画・レビュー＝品質保証）に、その時点で利用可能な最上位モデルを使い、手を動かす分割タスクでコストを下げる**のが基本方針。手戻りがコストになる難所では下位モデルをケチらない。

モデルのラインナップは時期により変わるため、**特定のモデル名に依存せず「最上位／上位／下位／最安」の相対ティアで判断する**。各役割には「その時点で利用可能な中で該当ティアの最良モデル」を割り当てる。下表のモデル名はあくまで現時点の目安で、利用可能なモデルが変わったら読み替える。

| 役割 | モデル方針（ティア） |
|------|-----------|
| オーケストレーター（メイン） | 最上位〜上位。判断の質を優先する。 |
| 計画作成 | **必ず最上位（その時点で最も高性能なモデル）。** 計画の誤りは全工程に波及するため妥協しない。 |
| 計画レビュー | **必ず最上位。** 妥協しない。 |
| 実装レビュー | **必ず最上位。** 妥協しない。 |
| レビュー二次（ダブルチェック） | **Codex**（独立した別エージェント）で一次レビューを突き合わせる。実装者の自己レビューにしない。 |
| 実装 | `implementer` サブエージェント（下位モデル、昇格条件で上位〜最上位へ。パートナーAIへの実装移譲は廃止 2026-07-12）。 |
| 調査・機械的作業（grep 調査、行末修復、定型修正） | 最安で十分。設計理解を伴う調査は中位以上。 |

> モデルはバージョン付きIDで固定しない（ラインナップは変わる。2026-07-04 設定）。サブエージェント定義は品質役 = `model: inherit`（メインセッションと同モデル）、作業役 = `sonnet`・`haiku` エイリアス。**メインセッションを常に利用可能な最上位で運転すれば品質役は自動追従する。** メインを節約モデルで走らせる例外時は、品質役に最上位エイリアスを明示指定する。同一フェーズで反証・手戻りが2回続いたら、回数を重ねず上位モデルへ昇格して仕切り直す。

> **実装は `implementer` へ委譲する**（クロスCLI実装移譲は廃止 2026-07-12）。レビューは Claude 一次＋Codex 二次（直接 CLI）のダブルチェックにする（→ `orchestration.md`「実装委譲とレビューのダブルチェック」）。

**難易度ベースの昇格ルール**: 実装・調査タスクでも、次のいずれかに該当し、間違えたときの手戻りコストが大きいものは上位〜最上位モデルへ昇格を検討する — Public API 変更、RHI/Vulkan、スレッド/同期、所有権・寿命管理、ジョブスケジューリング、アセットロード、シェーダーパイプライン、Object/Resource 寿命。「安いモデルで手戻りを繰り返す」より「最初から上位モデルで一発で通す」方が総コストが低い場面では迷わず昇格する。

## モデルプロファイルの2層設計(2026-07-25 新設、ユーザー方針)

ハーネスは「あらゆるモデルに同一の運転を課す」設計ではなく、**共通骨格+モデル別プロファイル**の
2層で運用する。モデル世代交代でチューニングし直すのは調整層だけ — 不変層は動かさない。

**不変層(どのモデルでも変えない)** — リポジトリ安全と事実確認の規律:
- ブランチ規律・プッシュしない(コミットまで)・ignored-tracked ガード・CLAUDE/AGENTS ミラー一致
- アウトカムゲート: ビルド/テストを**実行**し実出力を貼る。モデルがどれだけ賢くても、
  環境の事実(このリポジトリで通るか)は実行でしか得られない
- 独立レビュー(実装した本人以外の目): 盲点対策であり、モデルの自己検証の深さでは代替されない
- 証拠ベース報告・停止条件(同一手法2回失敗で停止)

**調整層(プロファイルで可変)** — プロセス指示の濃度:
- プロンプト内の自己検証・ダブルチェック**指示**の量(アウトカムゲートとは別物 —
  「実行して確かめろ」は不変層、「答える前にもう一度見直せ」系の指示はこちら)
- reasoning effort / thinking 予算の既定
- レビュー往復回数・トリアージ既定(LIGHT/STANDARD/HEAVY の運用閾値)
- 委譲粒度(1子に渡すタスクの大きさ)

**実装場所(2026-07-26)**: 切り替えは Claude 側 SessionStart フック
(`.claude/hooks/session-start-reminder.mjs`)が行う。SessionStart ペイロードの `model` で
プロファイルを選び、**選んだ名前を必ず出力する** — 検出できたかどうかがセッション冒頭で見える。
`model` を返さないホストや未知のモデルは `default` へ落ちる(未知のモデルに緩い規則を渡さない
安全側)。試運転・意図的な指定は `CLAUDE_MODEL_PROFILE=<name>` で上書きできる。
不変層の行はプロファイルに関わらず常に出力され、**差し替わるのは調整層の行だけ**。
Codex 側は GPT 系のため対象外(既存の `CODEX_MODE` 分岐がその役割を担う)。

### プロファイル: Opus 5(2026-07-26 更新 — 【一次資料】で裏どり済み)

出典: Anthropic 公式「Prompting Claude Opus 5」
https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
および「Effort」https://platform.claude.com/docs/en/build-with-claude/effort

**位置づけ — オーケストレーター席に向かないモデルではない**: 「complex agentic coding 向けに
作られ、**long-horizon agentic タスクに特に強い**」「**サブエージェントのチームをうまく統率する**
(writer-verifier パターンが有効に働き、エージェント同士の上書き事故が少ない)」。
1M コンテキストで指示追従・ツール呼び出し・推論が窓全体を通して一貫、とも明記 —
長時間セッションの劣化を前提にした足場は不要。ガイドが外せと言っているのは**役割ではなく儀式**。

**外すもの(公式が名指し)**:
- 「非自明なタスクには最終検証ステップを入れよ」「検証にサブエージェントを使え」型の指示。
  Opus 5 は言われなくても自己検証するため、指示すると**過剰検証**になりトークンを捨てる。
  公式は「**legacy harness scaffolding that adds separate verification steps**」も同罪と明記 —
  本ハーネスでは phase-gates の出口ゲートと verifier 役がこれに当たる。
- 「答える前に再確認せよ」「ダブルチェックせよ」型の自己再検査指示(自己修正は既に高精度)。
- 自分で数ツール呼び出しで終わる仕事の委譲。Opus 5 は**旧世代より積極的に委譲する**ので、
  委譲の適用条件を明示するか**上限を決め打ちする**ことが推奨されている
  (Codex 側 Sol ultra で実測した「58ロールアウト中45が子」と同じ失敗形状)。

**外さないもの(公式が推奨、または対象外)** — 境界は「自己検証か否か」:
- **アウトカム検証**(ビルド/テストを実行して実出力を貼る)。これは自己検証ではなく
  環境からの事実取得で、公式の言う「検証ステップ」の対象外。
- **他エージェントの成果物への独立レビュー**。公式は writer-verifier パターンを**有効と評価**
  している。禁じられているのは「**自分の**出力を検証するための子」。本ハーネスの
  「実装担当とレビュー担当は必ず別エージェント・自己レビュー禁止」はこの線の正しい側。
- **スコープ拘束**。公式は「Opus 5 は頼まれていない範囲まで広げることがある。狭いタスクでは
  スコープを明示的に制約せよ」と明記 — 5行宣言+check-scope はまさにこれで、**強化対象**。
- **レビューの全件報告+別パスで選別**。公式は「『重大なものだけ報告』と書くとその通りに
  報告量を絞る。全件 report させて別パスで filter せよ」。収束規則(blocking/non-blocking 分類、
  blocking のみ修正必須)はこの形と一致。

**追加が要るもの(Opus 5 固有の癖)**:
- **長さの較正**: ユーザー向け応答も**ディスク上の文書も**旧世代より長くなる。
  effort を下げても応答長は縮まない(公式明記)ため、**長さはプロンプトで制御する** —
  「必要な実質を満たし、水増しの節・重複要約・定型文で膨らませない」型の明示。
- **ナレーションの調子**: 作業中の実況が多い。更新の頻度と形を明示する
  (否定形の指示より、望む形の実例を示す方が効くと公式)。

**エフォート(伝聞の訂正)**: 「high より medium が高性能」は**誤り**。公式は
「**既定の `high` から始め**、eval に基づいて調整。**難度の高いコーディング/エージェント作業は
`xhigh` へ上げる**。`low`/`medium` は**品質が保てる範囲でのコスト・レイテンシ制御の主レバー**
として遠慮なく使う」。medium は「同品質ならより安い」であって「より高性能」ではない。
ただし Opus 4.8 の推奨は「コーディング/エージェントは xhigh から始めよ」だったので
**既定は一段下がった** — 伝聞はこの変化を歪めたものと思われる。
旧世代から effort をそのまま持ち越さず、**自前 eval で sweep し直す**のが公式の指示。

**現時点の運用**: 既定(二次レビューの `claude -p --model opus` 等)は**未変更**。
上記は「何を外し何を残すか」の一次資料に基づく設計判断材料であり、実際の配線変更は
ユーザー決定 + intake 手順3(自前 eval での実走比較)を経てから行う。

## 新モデル受け入れ手順(model intake、2026-07-25 新設)

大規模モデルのリリースは頻繁ではない。リリース時に1回、以下を通してから常用へ組み込む:

1. **可用性の実測**: CLI からの到達性(エイリアス追従/実 ID)、spawn 対応、effort 指定。
   推測で書かず実測して記録する(実例: Terra の綴り、Luna は spawn 不可)。
2. **仮説リストの作成**: 公式ガイダンス+コミュニティ報告を証拠等級【ベンダー主張】/
   【ユーザー観察(伝聞)】付きで本書に記録する。この時点では既定を変えない。
3. **実走評価**: model-evals.md の代表タスク(なければ直近マイルストーンから1件蒸留)を
   (a) 現行プロファイル (b) 仮説反映プロファイル の両方で実走し、差を記録する。
4. **プロファイル確定**: 実測に基づき**調整層だけ**を更新する。不変層は動かさない。
5. **配線更新**: ルーティング表・リマインダー・委譲既定へ反映し、本書に観測記録を追記する。

適用中の intake: **Opus 5**(手順1〜2完了 — エイリアス追従を実測、プロファイルは
公式一次資料で確定。**手順3(自前 eval での実走比較)待ち**で、既定はまだ変更していない)。
